## آثار جانبية تحتاج تمييزًا

1. **مشغل التدقيق وCHECK قد يعطلان حذف parent:** orders AFTER UPDATE/DELETE وpayments AFTER DELETE ينشئان financial_audit_log. هذا الجدول نفسه متعلق بالtenant المحذوف. يجب قياس error وatomic rollback وsnapshot كاملة؛ HTTP500 للحذف ليس إثبات رفض JWT للحساب المحذوف. FK CASCADE وصف graph، لا وعد بنجاح المعاملة. كذلك CHECKs orders_customer_required_when_unpaid / orders_courier_requires_courier_id / orders_courier_requires_customer_id في20260626155319 قد ترفض SET NULL إذا بقي order مدين/courier أثناء المعاملة؛ NOT VALID لا يعفي UPDATE الجديد. لا ترحيل لاحق في هذا المصدر يسقطها، ولا تستورد إصلاح PR49 غير المتكامل إلى الخريطة.
2. **المراجع قد تتغير دون محو السجل:** حذف أي هوية Auth، مالك أو غير مالك، ينفي created_by nullable في السجلات الباقية؛ غير المالك لا يضيف cascade الملكية. ينفي created_by في orders/payments/expenses، وorders.updated_at قد يتغير مع audit addition؛ لا تتوقع تطابق كل البصمات حرفيًا إذا كان عقد الاختبار يسمح بهذه metadata mutations. العقود المالية تحتاج comparison مستقل عن identity metadata.
3. **لا cascade لمراجع JSON/email:** audit before/after/details، email_send_log.recipient_email/metadata، suppression/unsubscribe وقوائم pgmq يمكن أن تبقى بعد حذف الحساب. لا policy لاحقة تضمن تنقيتها. ليست مالية7tables، لكنها privacy/traceability decisions غير محسومة.
4. **اشتراك خارجي:** subscriptions row محلي قد يحذف بـCASCADE؛ ذلك لا يثبت إلغاء Paddle خارجيًا. webhook يحاول mapping/upsert/update لاحقًا؛ لا callback حذف/إلغاء متصل بحذف Auth/tenant. تسوية billing خارجي تحتاج قرار منفصل ضمن العقد، لا اتصال أو عملية دفع هنا.
5. **مراجع بين متاجر غير متسقة:** FKs على customer_id/courier_id/product_id/order_id مفردة وليست composite tenant FKs. إن وجدت روابط غير متسقة في بيانات أخرى، أثر CASCADE/SET NULL يتبع id ولا يقتصر تلقائيًا على tenant_id؛ لا ندعي وجودها أو اختبار حماية مالية غير فارغة بين المتاجر. راجع كل inbound reference في المخطط والعينات المعزولة اللاحقة.
6. **Auth/storage:** لا يكشف public migration chain كل علاقات provider-owned schemas. لا فحص بيانات أو schema حي. [Supabase admin docs](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser) تفصل shouldSoftDelete عن الحذف النهائي؛ [managing user data](https://supabase.com/docs/guides/auth/managing-user-data) توضح أن JWT غير المنتهي ليس revoked بمجرد الحذف وأن storage ownership قد يعطل الحذف. هذه وثائق عامة حالية لا substitute لعقد Auth2.188.1؛ محاولة جلب مصدر tag عبر web لم تنجح، لذلك لا ندعي تدقيق كل provider FK.

## المخاطر والتوصية

- **High / design blocker:** لا approved owner deletion/retention/identity contract، مع cascade graph إلى المالية وaudit. يلزم قرار قبل جعل source expectations PASS آمنًا.
- **Medium / test-design risk:** audit-trigger FK rollback أو فقد created_by/raw UUID يحرف false acceptance إن اعتُبر HTTP denial أو unchanged counts كافيًا. التصميم التالي يفصلها.
- **Medium / privilege reconciliation:** historical authenticated TRUNCATE grant؛ no browser reachability proof. سجّل لتسوية gate catalog، دون تحويلها إلى incident أو تجاوز حدود الدفعة.
- **Unverified:** provider-owned FKs/storage/OAuth/session cleanup،nonempty financial history،in-flight/concurrency،production/Cloudflare. broad isolation/release remains blocked.

**التوصية الواحدة التالية:** يسجل المالك قرار OWNER-RETENTION-01 يحدد مصير متجره وسجله المالي وهوية التدقيق عند إغلاق حسابه. التوصية المقترحة للمناقشة: الاحتفاظ بالسجل والمتجر مع تعطيل وصول المالك إلى أن يُعتمد عقد حذف/نقل واضح؛ هذا **اقتراح غير معتمد**، ولا ينشئ مدة حفظ أو authorization لتنفيذه. بعد القرار فقط تُحوّل TEST_SPEC إلى أصغر دفعة اختبار مأذونة. لا تنفيذ مالي أو حذف أو إصلاح في هذه الدفعة.
