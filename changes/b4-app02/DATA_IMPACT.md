# B4 / APP-02 data impact

New private receipt ledger and tenant binding stores event/env/type/occurredAt, minimal normalized request/resolved billing state, outcome and projection flag; no raw webhook, emails, customer addresses, management URLs, secrets or signature. No deletion or original-row migration rewrite/backfill. Existing subscription global unique key stays. Private rows have no new FK that changes existing deletion/retention semantics; function validates actual tenant owner before new writes. Closed/banned owners may still have backend billing records updated; no auth access is restored. Financial tables remain empty in fixtures.

Legacy rows lack provider event time. Preserve original updated_at as a conservative initial floor in the receipt; older differing state is retryable ambiguous, exact state can repair missing cache without lowering the floor. Once known provider time advances beyond the floor, older events are durably stale. This is not proof of historical provider chronology or production reconciliation.

Provider timestamps are accepted through6fractional digits (PostgreSQL microseconds), retained as input strings; greater precision is rejected. Initial legacy server floors assume approximately synchronized clocks, are conservative acceptance barriers rather than provider watermarks, never lowered by retry/repair/no-op, and can require trusted reconciliation. A learned provider createdAt is immutable for the same subscription ID.

Binding/consumer contract: private bindings apply to live cache only. Only created may replace a non-null current subscription, ordered by immutable provider creation time. Updated/canceled non-current streams may persist without rebinding. A late created notification binds the latest stored stream state, never its stale payload. New subscription rows explicitly store provider creation time in public created_at for the existing billing sort; existing rows are never rewritten. Equal creation times across IDs fail before insertion. Legacy arrival timestamps that would make a created subscription disagree with the existing billing sort are rejected in both environments; a live projection also fails when another row would win that sort. These conservative barriers may require trusted reconciliation, not guessed chronology. Non-current stream persistence does not promise cache/UI agreement. Historical receipt identity cannot be reused in another environment or bootstrapped again after its public row is absent.
