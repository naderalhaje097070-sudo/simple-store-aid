# خطة المراجعة والاختبار الشامل لـ منجز V2

الهدف: التأكد أن كل صفحة تعمل، وكل تدفق مالي صحيح منطقيًا، وأن الأمان (RLS + RPC) محكم، وأن الواجهة تخدم فكرة "دفتر ذكي لصاحب محل صغير".

## 1) مراجعة الواجهات (UX/UI)
- فحص جميع المسارات: `/`, `/auth`, `/guide`, `/onboarding`, `/app` (كل الشاشات الفرعية: البيع، المخزن، العملاء، الديون، العهدة، التسويات، المحصل، إغلاق اليوم، المصاريف، المناديب، الإعدادات).
- التحقق من:
  - RTL سليم بدون scroll أفقي على 360/390/768/1280px.
  - أرقام LTR داخل سياق RTL (`.num`).
  - حالات فارغة (Empty States) في كل شاشة بدل الفراغ.
  - حالات تحميل/خطأ (Error Boundary + رسائل عربية واضحة).
  - عملة موحّدة: دينار ليبي (د.ل) في كل مكان.
  - أهداف اللمس ≥ 44px، تباين الألوان AA.

## 2) المراجعة المنطقية المالية (Black-box عبر RPCs)
إعادة تشغيل سيناريوهات S1–S18 على بيانات نظيفة:
- بيع نقدي مباشر، بيع بدين، بيع جزئي.
- تحصيل دين كامل/جزئي + منع تجاوز المتبقي.
- تسليم مندوب: كلي/جزئي/مرتجع، تسوية بمبلغ، ترحيل الفرق لديون العميل.
- منع إرجاع طلب مندوب فيه `collected_by_courier > 0` (S13 المُصلَح).
- إغلاق اليوم: تطابق `sales/collected/expenses/realized_profit/customer_debts/unsettled_custody` مع جداول DB.
- المخزون لا يصبح سالبًا، السعر مأخوذ من DB لا من العميل.
- التراجع (Undo) للمبيعات الأخيرة يستعيد المخزون ويُلغي الـ payment.

## 3) المراجعة الأمنية
- تشغيل Security Scanner واستعراض النتائج.
- التحقق من:
  - RLS مُفعّل على كل جدول `public.*` وسياسات scoped بـ `current_tenant_id()`.
  - GRANTs صحيحة (لا anon على جداول tenant).
  - كل RPC حساس عليه `_assert_staff` ولا يُمنح لـ anon.
  - عزل Multi-tenant: مستأجر لا يرى/يعدّل بيانات مستأجر آخر (اختبار بحقن `tenant_id` غريب).
  - `handle_new_tenant` + idempotent onboarding (لا duplicates).
  - رسائل الخطأ عربية ولا تسرّب SQL.
  - Auth: لا email enumeration، لا أدوار من جهة العميل.

## 4) فحص الصفحات الحرجة برمجيًا
- Playwright على Mobile (390px) و Desktop (1280px):
  - تسجيل دخول → Onboarding → /app.
  - تنفيذ بيع كامل، تحصيل دين، تسوية مندوب.
  - فتح كل تبويب والتأكد أنه يرسم محتوى (لا شاشة بيضاء).
  - التقاط console errors و network 4xx/5xx.

## 5) التوافق مع فكرة "دفتر ذكي"
مراجعة هل الشاشات تخدم 4 طبقات: المبيعات / المدفوع / ديون العملاء / عهدة المناديب — بوضوح ولغة صاحب المحل (لا مصطلحات ERP).

## 6) المخرجات
- تقرير `docs/full-system-review.md` يشمل:
  - جدول نتائج كل شاشة (Pass/Warn/Fail) + لقطات.
  - جدول S1–S18 محدّث + أي اختلاف عن DB.
  - قائمة Findings أمنية مع severity واقتراح إصلاح.
  - قائمة UX gaps مرتبة بالأولوية.
- قرار نهائي: **Ready / Ready with minor fixes / Not Ready** + قائمة الإصلاحات المطلوبة قبل التشغيل.

## 7) ما لن يُغيَّر في هذه المرحلة
- لن أُعدِّل كودًا أو schema. هذه مرحلة مراجعة فقط. أي إصلاح مكتشف يُسجَّل في التقرير ويُنفَّذ بعد موافقتك في جولة build مستقلة.

## التفاصيل التقنية
- أدوات: `supabase--read_query` + `security--run_security_scan` + Playwright headless داخل sandbox + قراءة ملفات الراوتر.
- بيانات الاختبار: مستخدم Pilot الحالي (tenant موجود) — بدون إنشاء مستأجرين جدد.
- لا أُشغّل migrations ولا RPCs تعديلية خارج سيناريوهات QA المعزولة.
