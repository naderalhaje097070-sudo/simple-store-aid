# قائمة تدقيق جاهزية التنفيذ — Mongezz / منجز

> Checklist مرجعية قبل البدء بتطوير الإصدار الحقيقي من **منجز**.
> تغطّي: القواعد المالية، Mobile-first، RTL، الأمان، والـ UX.

استخدام: ضع ✅ بجانب كل بند بعد التحقق منه فعليًا (لا على الورق فقط).

---

## 1. القواعد المالية الحرجة (Financial Invariants)

### 1.1 فصل الطبقات الأربع

- [ ] **المبيعات** (إجمالي الفواتير) لا تُحسب كمحصّل تلقائيًا.
- [ ] **المحصّل** = مجموع `payments.amount` فقط، لا من `orders.total`.
- [ ] **ديون العملاء** = `order.total − order.paid` لكل فاتورة، لا تُخلط مع العهدة.
- [ ] **عهدة المندوب** = `orders` بحالة `out_for_delivery` غير مُسوّاة، شاشة مستقلة.
- [ ] لا يوجد أي مكان في الواجهة يجمع بين دين عميل وعهدة مندوب في رقم واحد.

### 1.2 الربح

- [ ] **الربح المحقق** يُحسب من المحصّل فقط، لا من الفواتير المُصدرة.
- [ ] **الربح المتوقع** (إن عُرض) معلّم صراحة كـ"متوقع/تقديري" مع تنبيه.
- [ ] لا تظهر كلمة "ربح" بدون تحديد نوعه (محقق/متوقع).

### 1.3 الدفعات (Payments)

- [ ] كل عملية تحصيل تنشئ سجل `Payment` بـ `method` (نقدي/تحويل) و`order_id`.
- [ ] تسوية المندوب تولّد `Payment` بنفس البنية (لا سجل منفصل).
- [ ] breakdown المحصّل في الواجهة مشتق من `payments` الفعلية لا من قيم ثابتة.
- [ ] timeline حركة المال يقرأ من `payments` مرتبة بالوقت.

### 1.4 قيود لا تُكسر (DB Constraints)

- [ ] `CHECK (paid >= 0 AND paid <= total)` على جدول `orders`.
- [ ] `CHECK (quantity > 0)` على `order_items`.
- [ ] `CHECK (amount > 0)` على `payments` و`expenses`.
- [ ] منع `UPDATE/DELETE` على فاتورة موجودة ضمن `day_close` مُغلق (trigger أو RLS).
- [ ] منع بيع منتج بكمية > `stock` (trigger ذرّي على `order_items`).

### 1.5 العميل الإجباري

- [ ] لا يمكن حفظ فاتورة بـ `paid < total` بدون `customer_id`.
- [ ] لا يمكن حفظ فاتورة تذهب لمندوب بدون `customer_id`.
- [ ] إضافة عميل سريع: الاسم إجباري، الهاتف اختياري + كشف تكرار.

## 2. Mobile-First

### 2.1 الأحجام والـ Touch Targets

- [ ] التصميم الأساسي مبني على 360px–390px أولًا، ثم يتوسّع.
- [ ] كل زر/عنصر قابل للضغط ≥ 44×44px.
- [ ] لا توجد روابط نصية صغيرة كأهداف ضغط أساسية.
- [ ] المسافة بين الأزرار المتجاورة ≥ 8px.

### 2.2 شاشة البيع السريعة

- [ ] شبكة منتجات 3 أعمدة على 360px بدون كسر.
- [ ] حقل البحث `auto-focus` عند فتح الشاشة.
- [ ] عند focus على البحث: TopBar يختفي والنتائج تبقى مرئية فوق لوحة المفاتيح.
- [ ] أزرار +1 / +5 متاحة بدون فتح modal.
- [ ] زر "حفظ الفاتورة" ثابت في الأسفل (sticky)، لا يُغطّى بالكيبورد.

### 2.3 الأداء على الموبايل

- [ ] First paint < 2s على 3G محاكاة.
- [ ] لا scroll أفقي على أي شاشة بعرض 360px.
- [ ] صور المنتجات lazy load أو placeholders.
- [ ] قوائم > 50 عنصر تستخدم virtualization أو pagination.

### 2.4 Forms على الموبايل

- [ ] `inputmode="numeric"` على حقول الأرقام (مبالغ، كميات، هاتف).
- [ ] `type="tel"` على حقل الهاتف.
- [ ] `autocomplete` مناسب لكل حقل.
- [ ] خطأ التحقق يظهر تحت الحقل مباشرة، لا في toast بعيد.

---

## 3. RTL (الاتجاه من اليمين لليسار)

### 3.1 التخطيط

- [ ] `<html dir="rtl" lang="ar">` على مستوى الـ root.
- [ ] استخدام `start/end` بدل `left/right` في Tailwind (`ms-*`, `me-*`, `ps-*`, `pe-*`).
- [ ] الأيقونات الاتجاهية (سهم رجوع، next/prev) معكوسة بصريًا.
- [ ] القوائم والـ Drawers تنفتح من اليمين.

### 3.2 الأرقام والعملة

- [ ] الأرقام تظهر بـ LTR حتى داخل نص عربي (`<bdi>` أو `dir="ltr"`).
- [ ] العملة (ر.س / ج.م / إلخ) في جهة ثابتة (يسار الرقم عادةً).
- [ ] التواريخ بصيغة واضحة محليًا (هجري/ميلادي حسب اختيار المحل).
- [ ] فواصل الآلاف بالشكل المحلي (1,000 أو ١٬٠٠٠ حسب الإعداد).

### 3.3 الخط واللغة

- [ ] خط عربي مقروء (Cairo / Tajawal / IBM Plex Arabic) محمّل بـ `font-display: swap`.
- [ ] أحجام النص ≥ 14px للنص الجسمي، ≥ 16px للأرقام المالية.
- [ ] لا مصطلحات محاسبية ثقيلة (لا "ذمم"، "قيود يومية"، "أستاذ مساعد").
- [ ] الكلمات المفتاحية: "محصّل"، "مدفوع"، "متبقي"، "عهدة"، "موقوف العرض".

---

## 4. UX / شعور المستخدم

- [ ] الرئيسية = مساعد يومي بتنبيهات ذكية، لا تقرير ثقيل.
- [ ] رحلة بيع كاملة < 10 ثوانٍ (اختبارها بعداد على جهاز فعلي).
- [ ] Undo فوري بعد البيع (toast لمدة 5 ثوان على الأقل).
- [ ] رسائل النجاح تذكر المبلغ والطرف صراحة.
- [ ] تنبيهات: ديون > 30 يوم، مخزون منخفض، عهدة معلقة > 24 ساعة.
- [ ] Day Close يحفظ snapshot ثابت لا يتأثر بأي تعديل لاحق.

---

## 5. الأمان (Security)

### 5.1 Auth و RLS

- [ ] كل جدول في `public` لديه RLS مفعّل + policies.
- [ ] كل جدول مرتبط بـ `tenant_id`، وكل policy تتحقق من `current_tenant_id()`.
- [ ] الأدوار (`owner` / `staff`) تتحكم في الحذف وتعديل المنتجات والمصاريف.
- [ ] لا يمكن لمستخدم تغيير `tenant_id` الخاص به إلى tenant لا يملكه.
- [ ] `SECURITY DEFINER` functions غير قابلة للاستدعاء العام.

### 5.2 التحقق من المدخلات

- [ ] Zod schema على كل form قبل الإرسال.
- [ ] حدود طول واضحة (اسم منتج ≤ 100، ملاحظة ≤ 500، إلخ).
- [ ] لا `dangerouslySetInnerHTML` بأي محتوى مستخدم.
- [ ] أرقام الهواتف والمبالغ تُنظَّف من رموز غير رقمية قبل الحفظ.

### 5.3 رسائل الخطأ

- [ ] لا تظهر رسائل DB خام للمستخدم (لا "duplicate key violates...").
- [ ] رسالة عربية واحدة عامة + log تفصيلي في console للمطور فقط.

---

## 6. الموثوقية (Reliability)

- [ ] العمليات الحرجة (بيع، تحصيل، تسوية) ضمن transaction واحدة.
- [ ] لا "in-memory state" للأرقام المالية على الخادم.
- [ ] إعادة المحاولة (retry) على شبكة ضعيفة بدون تكرار الفاتورة.
- [ ] Idempotency key على إنشاء الفاتورة لمنع double-submit.

---

## 7. اختبار قبل الإطلاق

- [ ] اختبار حقيقي مع 3 أصحاب محلات (سيناريو يوم كامل).
- [ ] اختبار على جهاز Android منخفض المواصفات (RAM ≤ 3GB).
- [ ] اختبار شبكة بطيئة (Throttle 3G) لجميع الرحلات الأساسية.
- [ ] اختبار وضع عدم الاتصال على الأقل: عرض رسالة واضحة، لا crash.
- [ ] مراجعة محاسب مستقل للفصل المالي.

---

## 8. الشروط الإلزامية للإطلاق (Go/No-Go)

**لا يُسمح بالإطلاق إذا كان أيٌّ مما يلي غير محقّق:**

- [ ] الفصل المالي الأربعي محفوظ على مستوى DB لا UI فقط.
- [ ] RLS مفعّل على كل جدول مع tenant isolation.
- [ ] قيود `paid ≤ total` و`quantity ≤ stock` على مستوى DB.
- [ ] لا فاتورة دين بدون عميل.
- [ ] رحلة البيع < 10 ثوانٍ على جهاز فعلي.
- [ ] لغة الواجهة بشرية، خالية من مصطلحات ERP.
- [ ] Day Close يُنتج snapshot غير قابل للتعديل بأثر رجعي.
